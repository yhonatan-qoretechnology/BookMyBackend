Conectar el asistente de voz

Todo lo necesario para que la app hable con POST /api/assistant/chat: el flujo completo de audio, el formato exacto de los mensajes, el loop de tools y con qué proveedor probar hoy.

El flujo, de punta a punta

El backend nunca toca audio — solo entra y sale texto. Todo lo demás (voz→texto, texto→voz, el avatar) vive en la app.

Usuario habla → transcribir on-device con expo-speech-recognitionNo sube audio a ningún servidor. Es gratis y no suma latencia de red.

Por qué on-device y no un endpoint de audio

Transcribir o sintetizar voz en el servidor cuesta por minuto (además del costo del LLM) y suma segundos de latencia. On-device es instantáneo, gratis, y el audio del usuario nunca sale del teléfono. Si más adelante quieren una voz "premium" (ElevenLabs, etc.), eso sí necesitaría un endpoint nuevo — no está en el alcance de esta versión.

El endpoint

POST /api/assistant/chat

Content-Type
application/json
Authorization
Opcional. Bearer <token> si el usuario tiene sesión — habilita consultar_mis_citas y prioriza el límite por usuario en vez de por IP.
Rate limit
8 solicitudes / minuto (por usuario si mandás token, si no por IP). Headers X-RateLimit-Limit/Remaining/Reset en cada respuesta.
Ojo: existe también /api/assistant/chat/test

Es un endpoint aparte, solo para pruebas manuales desde Swagger — resuelve las tools él mismo del lado del servidor y devuelve la respuesta ya armada. La app NO debe usarlo nunca. La app siempre habla con /api/assistant/chat (este) y es ella quien ejecuta cada tool_call, como está documentado abajo.

Si te pasás del límite (429)

// Header: Retry-After: 51
{
  "statusCode": 429,
  "error": "Too Many Requests",
  "message": "Estás enviando mensajes muy rápido. Esperá 51 segundos e intentá de nuevo.",
  "retryAfterSeconds": 51
}

Usá retryAfterSeconds para deshabilitar el input y mostrar una cuenta regresiva ("Esperá 51s...") en vez de un error genérico. No hace falta parsear el mensaje de texto — el número ya viene aparte.

Request

// El array NO incluye el mensaje "system": lo agrega el backend.
{
  "messages": [
    { "role": "user", "content": "Quiero reservar una manicura" }
  ],
  "tools_enabled": true
}

Response

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "Tenemos manicura semipermanente por 25€...",
      "tool_calls": null // o un array, ver abajo
    }
  }]
}

content viene null cuando la respuesta es solo tool_calls — es normal, no es un error.

El loop de tools

Cuando tool_calls no es null, la app tiene que resolverlo y volver a preguntar. Es la parte con más detalle fino — un paso mal hecho y el modelo pierde el contexto.

  1. Ejecutar cada tool_call contra el endpoint REST correspondiente (tabla abajo) — ya existen todos, están tipados en services/apiBookmi.ts.

El detalle que rompe el loop si se olvida

Hay que reenviar el mensaje del assistant que pidió la tool — con su tool_calls — antes del mensaje tool con el resultado. Si se omite, el modelo no puede relacionar el resultado con el pedido y la conversación pierde el hilo.

{
  "messages": [
    { "role": "user", "content": "quiero manicura" },

    // 1) el turno del assistant que pidió la tool, tal cual llegó
    {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": { "name": "buscar_todo", "arguments": "{\"q\":\"manicura\"}" }
      }]
    },

    // 2) el resultado que ejecutó la app, como JSON en texto
    {
      "role": "tool",
      "tool_call_id": "call_abc123",
      "name": "buscar_todo",
      "content": "{\"servicios\":[{\"nombre\":\"Manicura SPA\",\"precios\":[...]}]}"
    }
  ]
}

Máximo 4 vueltas por turno de usuario — si se supera, cortá el loop y mostrá el último texto que haya llegado.

Cómo saber cuál responde
El campo choices[0].message no cambia entre proveedores — el backend normaliza la respuesta, no hace falta que la app sepa cuál está activo.
Backend: src/assistant/ en bookmy. Cualquier duda sobre una tool puntual o un caso del loop que no cierre, con el request_id/payload exacto se resuelve más rápido.
